### 10. 予約投稿が時刻どおりに公開されないことがある（2026-08-26に発生）

WordPressの予約投稿は**サイトへのアクセスを引き金に動く**ため、アクセスの少ない時間帯に
公開時刻が来ると、そのまま置き去りになる。実際に、日本時間 8/26 19:00 の記事が
6時間過ぎても `future` のままだった（同日12:00の記事は公開されていた）。

`.github/workflows/wpcron.yml` を追加して、**公開の枠の直後だけ** `wp-cron.php` を叩く。
日本時間 07:05 / 07:25 / 12:05 / 12:25 / 19:05 / 19:25 の1日6回。

常時叩く必要はない。枠が決まっているのだから、その直後だけでいい。
1枠2回にしてあるのは、GitHubの定期実行が時刻どおりに動かず、まれに落ちるため。
1回だけだと落ちたときに次の枠まで置き去りになる。

**枠（`tools/wp.py` の `SLOTS`）を変えたら、wpcron.yml の時刻も変えること。**

**定期実行は既定ブランチのワークフローしか動かないので、mainに入るまで効かない。**

## wp-cron を叩くだけでは予約は出ない（2026-08-27）

`wpcron.yml` を main に入れた翌朝、**9347が19時間半 future のまま止まっていた。**
同じ時間帯の9351・9352は出ている。つまり「wp-cronが動いていない」のではなく、
**その記事だけ予定が失われていた。**

WordPressの予約投稿は、記事ごとに `publish_future_post` という予定を仕込んで動く。
この予定が何かの拍子に消えると、wp-cron がいくら動いてもその記事は永久に出ない。
**wp-cron.php を叩く対策では、この形の失敗は拾えない。**

あわせて、GitHubの定期実行そのものも当てにならなかった。
main に入れてから丸1日で実行は1回だけ、時刻も枠と無関係だった（20:14 UTC）。

対策として `wp.py overdue` を足した。公開時刻を過ぎたのに future のまま残っている
記事を探して publish に変える。`wpcron.yml` の2つめの手順として毎回走る。
**pingが空振りしても、遅れは次の実行で拾える。**

- `overdue` … 見るだけ
- `overdue --apply` … 公開する

定期実行が落ちたときのために、**朝いちに `queue` を見る**のは続けたほうがいい。
予約の先頭が今日より前の日付になっていたら、それが止まっている記事。
